# DataCatalogue Project Instructions

## Project purpose

This project develops an advanced ASP.NET Core API solution for S-100-related data catalogue functionality.

The primary technology stack is:

- C#
- .NET 10
- ASP.NET Core 10
- ASP.NET Core Controllers
- ASP.NET Core built-in OpenAPI generation
- Scalar
- Swagger UI / Swashbuckle
- Eventuous
- Event sourcing where appropriate
- Serilog

The existing repository and architecture are the baseline for all work:

`https://github.com/S-100-BlueStack/S100Services/tree/DataCatalogue`

Eventuous is available at:

`https://github.com/Eventuous/eventuous`

When working from the GitHub repository, always treat previously read repository content as potentially stale. Re-read relevant files, commits, branches, or diffs when correctness depends on the current implementation.

# Program entry point

Never use top-level statements.

ASP.NET Core applications must use an explicit `Program` class and an explicit `Main` method.

Preferred structure:

```csharp
public static class Program
{
    public static async Task Main(string[] args)
    {
        var builder = WebApplication.CreateBuilder(args);

        // Configure services.

        var app = builder.Build();

        // Configure middleware.

        await app.RunAsync();
    }
}
```

Keep `Program.cs` small.

Move substantial service registration and middleware configuration into focused extension methods where appropriate.

Do not create abstractions around startup configuration unless they materially improve readability or maintainability.

---

# ASP.NET Core API style

Use ASP.NET Core Controllers as the default API style.

Prefer:

```csharp
[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
public sealed class ExampleController : ControllerBase
```

Do not convert controllers to Minimal APIs unless explicitly requested.

Use constructor dependency injection.

Controllers should remain thin.

Controllers are responsible for:

- HTTP concerns
- request binding
- authorization
- API response mapping
- selecting appropriate HTTP status codes

Business logic should normally live outside controllers.

---

# API versioning

Use the existing ASP.NET API versioning infrastructure.

Public API endpoints should normally be explicitly versioned.

Keep versioning visible in the API contract and OpenAPI documents.

Do not introduce a different versioning mechanism without a clear reason.

---

# OpenAPI architecture

ASP.NET Core's built-in OpenAPI generator is the authoritative source of the OpenAPI documents.

Do not maintain separate OpenAPI definitions for Scalar and Swagger.

There must be one OpenAPI description consumed by multiple UIs.

Conceptually:

```text
ASP.NET Core API
        |
        v
Built-in OpenAPI generator
        |
        +------------------+
        |                  |
        v                  v
     Scalar           Swagger UI
```

Use:

```csharp
builder.Services.AddOpenApi();
```

or the existing project equivalent.

OpenAPI transformers, schema transformers, operation transformers, and document transformers should be preferred when OpenAPI customization is required.

Do not use Swagger-specific mechanisms for something that belongs in the authoritative OpenAPI document unless no suitable built-in OpenAPI mechanism exists.

---

# Scalar

Scalar is the preferred interactive API documentation and API client.

When implementing API documentation functionality, prioritize a good Scalar experience.

Scalar should consume the OpenAPI description generated by ASP.NET Core.

Do not build a separate Scalar-specific API specification.

Where authentication support, examples, descriptions, schemas, or other metadata are added, ensure they work correctly in Scalar.

---

# Swagger UI

Swagger UI is retained as a secondary API documentation and testing interface.

The project currently uses Swashbuckle for Swagger UI support.

Swagger UI must consume the same OpenAPI description that Scalar consumes.

Do not allow Swagger/Swashbuckle to become a competing OpenAPI generation pipeline.

Avoid introducing:

```csharp
services.AddSwaggerGen();
```

for document generation if ASP.NET Core's built-in OpenAPI generator already provides the required functionality.

Swashbuckle should primarily provide Swagger UI functionality unless a specific requirement justifies otherwise.

---

# OpenAPI quality

Public API endpoints should have useful OpenAPI metadata.

Use XML documentation where it meaningfully improves API documentation.

Document:

- endpoint purpose
- parameters
- request models
- important response models
- significant HTTP status codes

Avoid documentation that simply repeats method or property names.

Prefer useful descriptions such as:

```csharp
/// <summary>
/// Returns the catalogue entry identified by the supplied identifier.
/// </summary>
```

rather than:

```csharp
/// <summary>
/// Gets catalogue.
/// </summary>
```

Add examples where they materially help API consumers understand the contract.

---

# HTTP API conventions

Use HTTP semantics correctly.

Prefer conventional responses such as:

- `200 OK` for successful reads
- `201 Created` for successful resource creation
- `202 Accepted` for genuinely asynchronous processing
- `204 No Content` where no response body is needed
- `400 Bad Request` for invalid input
- `401 Unauthorized` when authentication is required
- `403 Forbidden` when authorization fails
- `404 Not Found` when a resource does not exist
- `409 Conflict` for state/resource conflicts when appropriate
- `422 Unprocessable Entity` only when its semantics are specifically appropriate
- `500 Internal Server Error` for unexpected server failures

Do not return `200 OK` for errors merely to simplify client handling.

---

# ProblemDetails

Prefer ASP.NET Core `ProblemDetails` for HTTP API errors.

Keep error responses predictable and machine-readable.

Where appropriate, use:

```csharp
builder.Services.AddProblemDetails();
```

and ASP.NET Core's standard exception/problem-details handling.

Avoid inventing custom generic error envelopes unless the project has a concrete requirement that `ProblemDetails` cannot satisfy.

---

# DTOs and API contracts

Do not expose Eventuous aggregates, internal domain state, persistence objects, or infrastructure models directly through HTTP APIs.

Use explicit API request and response contracts.

For example:

```text
HTTP request
    |
    v
Request DTO
    |
    v
Application/domain operation
    |
    v
Response DTO
    |
    v
HTTP response
```

Keep public API contracts stable even if internal implementation details change.

Prefer immutable API contracts where practical.

Use records where they are an appropriate representation of data contracts.

---

# Eventuous

Eventuous is a primary architectural building block for event-sourced parts of the application.

However, Eventuous must not be forced onto functionality that does not benefit from event sourcing.

Use Eventuous for functionality involving concepts such as:

- aggregates
- domain state transitions
- commands
- domain events
- event streams
- event-sourced persistence

Do not use Eventuous merely as a generic abstraction around ordinary stateless services.

---

# Eventuous command flow

Prefer an architecture similar to:

```text
Controller
    |
    v
Command/Application service
    |
    v
Eventuous aggregate/state
    |
    v
Domain events
    |
    v
Event store
```

Controllers should generally call application or command services rather than manipulating Eventuous state directly.

Domain decisions should remain outside the HTTP layer.

---

# Eventuous version compatibility

Do not assume Eventuous APIs from memory.

Eventuous evolves and may introduce breaking changes.

Before using unfamiliar Eventuous APIs:

1. inspect the version referenced by the current project;
2. inspect the current code or documentation for that version where necessary;
3. implement against the version actually installed in the project.

Do not silently upgrade Eventuous.

Any dependency upgrade should be deliberate and clearly explained.

---

# Event store

The project already has an Eventuous `InMemoryEventStore` implementation.

Use the existing InMemory implementation unless the task specifically requires another event store.

Do not recreate an InMemory event store if an appropriate implementation already exists.

Architecture should avoid unnecessary coupling to the InMemory implementation so that persistent storage can be introduced later.

However, do not introduce speculative abstractions solely for a hypothetical future event store.

---

# Application architecture

Preserve the existing project and solution structure by default.

Do not automatically reorganize the repository into:

```text
Api
Application
Domain
Infrastructure
```

or another textbook architecture.

Introduce new projects or layers only when they provide clear value.

Prefer the smallest architectural change that maintains good separation of concerns.

When adding functionality, first determine where equivalent functionality already lives in the solution.

Follow existing patterns where they are reasonable.

# Dependency injection

Use ASP.NET Core's built-in dependency injection container.

Register dependencies with the narrowest appropriate lifetime:

- Singleton
- Scoped
- Transient

Do not use service locator patterns.

Do not resolve application dependencies manually from `IServiceProvider` unless framework integration genuinely requires it.

Prefer strongly typed dependencies through constructors.

---

# CancellationToken

Propagate `CancellationToken` through asynchronous operations where cancellation is meaningful.

Controller actions should normally accept:

```csharp
CancellationToken cancellationToken
```

and pass it to downstream asynchronous APIs.

Do not create arbitrary `CancellationTokenSource` instances when the HTTP request cancellation token is appropriate.

---

# Async code

Use asynchronous APIs for I/O operations.

Avoid:

```csharp
.Result
.Wait()
.GetAwaiter().GetResult()
```

in normal application code.

Use `async` and `await`.

Do not make methods asynchronous when they contain no asynchronous work.

---

# Validation

Perform validation at appropriate boundaries.

Simple API input validation may use ASP.NET Core model validation.

Domain invariants belong in the domain/application layer and must not depend solely on controller validation.

Do not duplicate the same validation logic throughout multiple controllers.

Return useful `ProblemDetails` responses when API input is invalid.

---

# Logging

Use the existing Serilog infrastructure.

Prefer structured logging:

```csharp
logger.LogInformation(
    "Processing catalogue {CatalogueId}",
    catalogueId);
```

instead of string interpolation:

```csharp
logger.LogInformation(
    $"Processing catalogue {catalogueId}");
```

Do not log secrets, access tokens, credentials, or unnecessarily sensitive payloads.

Log information useful for diagnostics and operations.

Avoid excessive logging of routine successful operations.

---

# Exceptions

Use exceptions for exceptional conditions, not ordinary control flow.

Do not broadly catch `Exception` unless the code is at an appropriate application boundary and there is a concrete reason.

Prefer centralized exception handling for HTTP error conversion.

Preserve original exception information when wrapping exceptions.

---

- .NET

- the libraries already used by the project

- correctness

# Testing

When existing tests cover the area being modified, update them as part of the change.

For ASP.NET Core API integration tests, prefer standard ASP.NET Core testing infrastructure such as:

```csharp
WebApplicationFactory<TEntryPoint>
```

Prefer xUnit when adding tests unless the existing test project uses another framework.

Do not introduce mocking frameworks or assertion libraries simply by default.

Use them only when they materially improve the tests or when they are already established dependencies.

Tests should focus on externally observable behavior rather than implementation details.

# Security

Use ASP.NET Core's standard security infrastructure.

Do not implement custom authentication or cryptography when established framework implementations exist.

Never hard-code:

- passwords
- API keys
- tokens
- secrets
- production connection strings

Use configuration and appropriate secret-management mechanisms.

Ensure security-related OpenAPI descriptions correctly represent the API's actual authentication behavior.

# Performance

Do not optimize prematurely.

Avoid obviously inefficient implementations, especially:

- unnecessary allocations in hot paths
- repeated enumeration
- unnecessary serialization/deserialization
- blocking asynchronous operations
- loading entire datasets where streaming or filtering is appropriate

Only introduce complex performance optimizations when there is evidence or a clear requirement.

For larger tasks, first briefly summarize the relevant existing architecture and explain how the change fits into it.

# Primary architectural principle

The project should evolve from the architecture that already exists rather than being repeatedly redesigned.

Prefer:

```text
existing architecture
        +
small coherent improvements
        +
ASP.NET Core conventions
        +
Eventuous where event sourcing provides value
```

over:

```text
large speculative framework
        +
unnecessary abstractions
        +
forced architectural patterns
```

The resulting API should remain understandable to an experienced ASP.NET Core developer without requiring extensive knowledge of custom infrastructure.
